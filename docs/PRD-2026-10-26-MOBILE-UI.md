# Mentora 移动端 UI / 交互 PRD

> **版本**：v1.0 · 2026-10-26  
> **状态**：Planned（规划中，本文不是已实现或已通过的发布证明）  
> **适用版本**：v21.1 之后的响应式 Web 迭代  
> **产品主线**：学习模式永远第一优先级；移动端是同一套学习资产在小屏上的任务投影，不是另一套产品。  
> **配套验收**：实现后在 `ACCEPTANCE.md` 增加移动端章节；自动化证据与真实设备证据必须分开记录。

---

## 0. 第一行判断

> **手机端不是把桌面端缩小，而是把同一份学习资产按手机任务重新排布。**

当前移动端的问题不是“少几个 `sm:` 类名”，而是桌面信息架构直接压缩到 320–430px 后，出现了四类结构性损耗：

1. **主任务不突出**：学习、复习、记笔记、对话的主要动作与次要信息争夺同一行。
2. **可用视口被侵占**：移动顶栏、底栏、safe-area、输入法和 fixed composer 没有统一的几何契约。
3. **桌面多栏没有真正重排**：第二大脑已有单栏 Tab 先例，但读书、圆桌、学习详情等页面仍把桌面横向关系压到手机上。
4. **失败路径没有得到同等设计**：慢网、流式挂起、键盘打开、浏览器返回、误触删除等情况，不能只靠 toast 或浏览器默认行为兜底。

本 PRD 的目标不是追求“每个页面都能挤进去”，而是建立一套可复用、可计算、可对抗验收的移动端 UI 契约。

## 1. 背景与现状证据

### 1.1 产品约束

以下决策继承当前产品路线，不在本 PRD 中重新争论：

- 学习闭环（引导 → 两级计划 → 每日一课 → 验收门 → FSRS 复习 → 掌握状态）是主力。
- 第二大脑、读书伙伴、人生伙伴和学习人生四个工作空间继续保留。
- 侧栏仍是桌面端稳定信息架构；移动端只做投影，不删除工作空间、不新增统一聊天首页。
- 圆桌当前准确命名是“多框架独立判断 + 主持人综合”，不是多轮辩论。
- 数据状态、AI 语义、Demo/真实模型边界在移动端与桌面端必须一致。
- 本阶段做响应式 Web UI，不做原生 App、PWA 推送、微信小程序或新的数据模型。

依据：`README.md:115-145`、`docs/PRD-2026-10-24.md:12-17,73-108,214-227`。

### 1.4 证据纪律

沿用仓库既有文档规范：

- 自动化测试只能证明代码性质；
- 浏览器自动化证明一条可重复路径；
- 真实 iOS Safari / Android Chrome 才能证明真实设备输入法、刘海和返回键行为；
- 设计完成、代码完成、自动化通过、人工实测通过、真实价值通过不能混写；
- 未验证项统一写 `⏳ NOT TESTED`，不能用“代码看起来没问题”替代。

参考：`ACCEPTANCE.md:1-10`、`docs/ACCEPTANCE-FOUNDER-FIRST-2026-10-24.md:25-32`。

## 2. 目标、非目标与成功定义

### 2.1 目标

在 320–430px 宽度、单手操作、系统键盘打开、网络慢或短暂断网的情况下，用户能够：

1. 从移动底栏找到并进入五个主工作空间；
2. 完成学习主线的关键闭环：新目标 → 引导 → 今日课 → 验收/迁移门 → 下一天；
3. 打开、编辑、保存和复习第二大脑笔记；
4. 在读书伙伴中选择当前章节、对话、完成三重验收；
5. 在人生伙伴中发起单人对话或三席圆桌，并在运行中停止；
6. 在任何输入法状态下看见当前输入框、发送按钮或停止按钮；
7. 在失败、取消、刷新、切页后知道发生了什么，且不产生跨会话写入或数据丢失。

### 2.2 非目标

本阶段不做：

- 原生 iOS/Android App；
- PWA manifest、离线壳、推送通知；
- 统一聊天首页或通用 Agent Router；
- 改变 AI 提示词、评分规则、数据 schema 或同步冲突策略；
- 删除桌面端侧栏、Cmd/Ctrl+K、四个工作空间；
- 把圆桌改造成真正的多轮席位互相辩论；
- 为了移动端美观而隐藏失败状态、削弱删除/跳过/注销确认。

### 2.3 成功定义

移动端适配只有在以下条件同时满足时才可宣称完成：

```text
M0 结构门禁通过
∧ M1 导航可达
∧ M2 几何无侵入
∧ M3 触控可用
∧ M4 学习主线通过
∧ M5 第二大脑通过
∧ M6 读书/圆桌通过
∧ M7 输入法通过
∧ M8 无障碍通过
∧ M9 数据与失败路径通过
∧ M10 性能门槛通过
∧ 真实设备关键矩阵通过
```

任何关键阻断项失败，结论只能是 `BLOCKED` 或 `PASS WITH EXPLICIT LIMITS`，不能写“基本适配”。

## 3. 移动端信息架构

### 3.1 导航决策：5 个主入口 +「更多」

移动底栏不再把 7/8 个入口等权塞在同一排。推荐结构：

| 位置 | 入口 | 主任务 |
|---|---|---|
| 1 | 总览 | 判断今天继续什么 |
| 2 | 学习教练 | 推进当前学习日/新建目标 |
| 3 | 第二大脑 | 记笔记/复习/找知识 |
| 4 | 读书伙伴 | 继续当前章节和对话 |
| 5 | 人生伙伴 | 发起单人对话/圆桌 |
| 6 | 更多 | 学习人生、设置、后台、账户/退出 |

规则：

- 桌面侧栏仍展示全部工作台和系统入口；移动端是导航投影，不是删除信息架构。
- 当前位于“学习人生 / 设置 / 管理后台”等隐藏入口时，“更多”显示 active 状态，并在抽屉中标明当前项。
- 管理员后台不单独挤占主底栏格位。
- 底栏固定在 visual viewport 底部，内容区显式预留底栏高度与 safe-area。
- 浏览器 Back 的优先级：先关闭「更多」或任意 sheet → 再返回上一页面；不能出现“返回键把用户直接带离但抽屉仍在视觉上打开”的状态。

### 3.2 移动顶栏

顶栏只承担定位和一个主要动作，不承担完整桌面侧栏功能：

- 左侧：详情页返回按钮，列表页显示 Mentora 字标；
- 中间：当前工作空间标题，长标题单行截断；
- 右侧：本页唯一主要动作或更多菜单；
- 顶栏使用现有 `.glass-chrome`，只在滚动后显示发丝边和阴影；
- 顶栏高度进入统一布局变量，不能由页面自行猜测。

### 3.3 页面层级规则

每个移动页面必须能回答：

1. 当前页面是什么；
2. 这一屏唯一主要任务是什么；
3. 完成任务的主要按钮在哪里；
4. 次要信息如何展开；
5. 失败后如何重试或恢复。

移动首屏原则：

```text
每个 viewport 只允许 1 个主要任务动作（PrimaryActionPerViewport ≤ 1）
```

不是禁止页面有多个按钮，而是不能让用户同时面对多个同等权重的“下一步”。

## 4. 设备矩阵与响应式契约

### 4.1 必测设备尺寸

| 标识 | viewport | 用途 |
|---|---:|---|
| XSmall | 320×667 | 最小宽度、长标题、最密集触控压力 |
| Small | 375×812 | 主验收基线，接近常见 iPhone 竖屏 |
| Medium | 390×844 | 常见 iPhone/Android 竖屏 |
| Large | 412×915 | 大屏手机、较长内容和底栏间距 |
| Landscape | 667×375 | 横屏、键盘和底栏高度压力 |
| Desktop regression | 1440×900 | 桌面侧栏和多栏不回归 |

真实设备至少覆盖：

- iOS Safari：含刘海安全区、系统键盘、浏览器返回；
- Android Chrome：含返回键、键盘 resize 行为、字体放大；
- 慢速 4G 与短暂 offline；
- `prefers-reduced-motion`、`prefers-reduced-transparency`、高对比度、200% 文本缩放。

### 4.2 统一 CSS/几何变量

建议在全局壳层提供以下变量，页面不得自行复制一组 `bottom-20` 或 `100vh` 经验值：

```css
:root {
  --mobile-topbar-h: 52px;
  --mobile-nav-h: 64px;
  --safe-top: env(safe-area-inset-top, 0px);
  --safe-bottom: env(safe-area-inset-bottom, 0px);
  --safe-left: env(safe-area-inset-left, 0px);
  --safe-right: env(safe-area-inset-right, 0px);
  --keyboard-inset: 0px;
  --mobile-content-bottom: calc(
    var(--mobile-nav-h) + var(--safe-bottom) + 16px
  );
}
```

变量名和具体数值可在实现阶段根据真实顶栏/底栏测量调整，但“统一来源”不可省略。

### 4.3 visual viewport 规则

实现 `useVisualViewportInset`（或等价共享 hook）：

- 监听 `visualViewport.resize` 与 `visualViewport.scroll`；
- 计算键盘打开造成的可视高度差；
- 组件卸载时移除监听；
- 浏览器不支持 `visualViewport` 时退化为 `0px`，不阻塞页面；
- 键盘打开时，focused input、发送按钮、停止按钮的底部必须落在 visual viewport 内；
- 键盘关闭后恢复原滚动位置，不把用户送到页面顶部或错误的消息位置。

### 4.4 宽度与溢出规则

- 页面根节点不得产生横向滚动：`document.documentElement.scrollWidth === window.innerWidth`。
- `overflow-x: clip` 只能作为最后一道保护，不能用来掩盖被截断的主内容。
- 代码块、表格、图谱等确需横向滚动的内容，必须在局部容器内滚动，并提供可见边界或滚动提示。
- 长标题、URL、Markdown 表格、用户输入和模型输出必须允许换行或省略，不得撑破卡片。

### 4.5 触控和可访问性尺寸

- 所有可操作元素的**命中盒**至少 44×44px；图标视觉尺寸可以小于 44px。
- 相邻独立目标之间至少 8px 间距；危险操作不得紧贴主要操作。
- 不得把 hover 作为手机上唯一的删除、展开、提示或导航方式。
- `:focus-visible` 保留现有靛蓝焦点样式；键盘和读屏顺序必须与视觉顺序一致。
- 动画、玻璃和阴影必须遵守已有 reduced-motion / reduced-transparency / contrast 规则。

### 4.6 viewport 元数据

实现阶段 `src/app/layout.tsx` 应显式声明：

- `width=device-width`；
- `initialScale=1`；
- `viewportFit=cover`；
- 与浅色设计系统一致的 `themeColor`。

这只是移动 Web viewport 契约，不等于实现 PWA。

## 5. 页面级产品方案

### 5.1 总览 `/`

**手机主问题**：我现在应该继续什么？

默认顺序：

1. 当前学习日/继续学习；
2. 待复习；
3. 当前读书；
4. 人生伙伴；
5. 学习热力墙和足迹。

规则：

- 第一屏不展示四个同等权重的大卡片；当前学习卡是唯一主卡。
- 空状态保留“开始第一个目标”作为主动作，“示例目标”和“连接模型”降为次要动作。
- 热力墙在小屏可以局部横向滚动，但不能让整个页面横向滚动。
- 卡片内的进度、标题、下一步按纵向或两行布局排列；不能依赖标题永不换行。

### 5.2 学习教练列表 `/learn`

**手机主问题**：开始或继续一个学习目标。

- “想学点什么”输入框与“开始引导”按钮在 320–390px 下纵向堆叠；按钮至少 44px 高，默认全宽。
- “聊出方向”折叠卡默认保持可发现，但不抢占新目标主入口。
- 目标卡采用三层结构：
  1. 进度与状态；
  2. 目标标题和方向；
  3. 下一步、完成度、每周时间。
- 删除动作不与进度环、标题、状态胶囊争夺同一行；进入明确的更多菜单或独立命中盒。
- 删除目标仍需二级确认；计划类笔记和知识点的保护选项在当前 viewport 内可见，不要求用户滚回顶部找确认按钮。

### 5.3 学习目标详情 `/learn/[id]`

**手机主问题**：完成今天这一日，而不是先读完整路径。

移动默认顺序：

1. 今日任务头部（状态、标题、方法）；
2. 今日学习文档；
3. 资源；
4. 随手记 / 问教练；
5. 验收；
6. 迁移题与下一天；
7. 路径设计（折叠为“任务导航”）。

规则：

- 桌面左侧 `PlanTimeline` 在手机默认折叠成“任务导航”按钮或 bottom sheet；用户仍可回看任意已解锁日。
- 当前 Day 是默认焦点；不能让用户先滚过完整阶段树才看正文。
- 资源卡中 URL、来源标签和“为什么”必须允许多行；不能用 `truncate` 把关键资源信息截断到不可理解。
- “开始验收”“跳过”“提交迁移题”是互斥的当前动作；危险的跳过动作仍需二次确认。
- 验收结果失败时，补课和重试按钮必须在当前结果卡内可见；不能只给 toast。
- 目标详情的 composer/问教练输入不能被底栏覆盖。

### 5.4 第二大脑 `/brain`

**手机主问题**：找到、理解、记录或复习一条知识。

保留现有三 Tab 先例：

- `列表`：搜索、文件夹、标签、笔记列表；搜索条吸顶。
- `笔记`：标题、阅读/编辑、实时预览、双链补全；长正文在内部滚动。
- `信息`：反链、出链、大纲、标签；不与正文同时挤在一屏。

规则：

- 打开一篇笔记后自动切到“笔记” Tab；从笔记跳回列表要保留搜索/文件夹状态。
- 编辑工具栏可横向滚动，但每个工具的命中盒至少 44px，并显示可访问名称。
- `[[` 补全下拉不能超出 visual viewport；键盘打开时下拉应贴近光标并可滚动。
- 图谱在手机上是独立 Tab/页面，不把画布和文件树并排缩小；缩放和拖拽手势不能阻塞页面滚动。
- 上传文档、AI 建联、AI 整理等次级动作进入工具栏的更多菜单，不能挤压标题输入框。
- 复习 Modal/Sheet 内的输入、出题、判分和“下一个”按钮始终可见或可滚动到；关闭后焦点归还触发元素。

### 5.5 读书书架 `/read`

**手机主问题**：选一本书继续读，或快速加入一本书。

- 书架使用单列卡片；卡片内只保留书名、状态、进度和下一步。
- “添加书籍”在顶栏或空状态中作为唯一主要动作；添加表单在手机纵向排列。
- 删除书籍不是 hover-only；确认后要给可理解的 toast/状态反馈。
- 粘贴内容的文本域可增长，但 Modal/Sheet 需要内部滚动并避开键盘。

### 5.6 读书详情 `/read/[id]`

**手机主问题**：围绕当前章节对话并完成理解验收。

- 默认先显示当前章节、焦点问题和对话；阅读路线折叠为 accordion 或 bottom sheet。
- 章节切换后返回对话位置，不把用户送回详情页顶部。
- 阅读模式胶囊允许横向滚动或分组折叠，不能撑破页面。
- 三重验收三题纵向排列，每题输入框至少 44px 可触控高度；提交后评分、建议和“重新验收”在同一结果上下文中。
- “提炼洞见”作为详情页单一次级动作，生成中可停止/重试，不能把整个页面置于不可交互状态。
- 对话 composer 使用统一 `MobileComposer` 契约，不再自行写 `bottom-20`。

### 5.7 人生伙伴 `/council`

**手机主问题**：把一个困惑交给某个伙伴或一个小圆桌。

- 会话历史从主流程前的左栏改为顶端“历史”抽屉/Sheet；打开单人或圆桌后，消息区优先占据首屏。
- 人物选择使用可搜索、可分组的 Sheet；默认三席仍是 Naval / Jobs / Taleb 的推荐组合，语义与桌面端相同。
- 圆桌并行席位在手机纵向排列；每席显示名称、状态、完成/失败/思考中；主持人单独显示。
- 运行中固定显示当前阶段、完成数、停止按钮；停止后保留已完成发言，明确写取消留痕。
- 切换会话、新建会话、删除会话必须继续遵守 `runId` 隔离；移动端只是改变布局，不改变状态机。
- composer 永远位于底栏和键盘安全区之上；停止按钮不能被消息流、底栏或助手挂件遮住。

### 5.8 学习人生 `/life`

- 时间线单列，事件详情不依赖 hover。
- 里程碑格子在 320px 下至少两列，避免四列文字缩成不可读的 10px。
- AI 教练动态按钮在生成中明确显示状态；失败时保留可重试动作。

### 5.9 设置 `/settings`

- 账户 / 模型 / 数据 / 推荐继续保留，移动端使用横向可滚动 Tab 或“设置项”列表，不把四个 Tab 压成小按钮。
- 账户、模型和密码表单全部纵向排列；保存按钮在对应区块末尾，必要时全宽。
- 数据导入、导出、云端恢复和清空操作分组；危险操作全宽、二次确认、错误状态在当前视口内可见。
- 注销账号的密码和二次确认不能因键盘打开而被底部按钮遮挡。
- 高风险动作不因移动端“简洁”而降级确认强度。

### 5.10 全局 Modal / Sheet / 助手

- 手机 Modal 默认 bottom sheet：顶部有拖拽/关闭语义，最大高度基于 `100dvh` 和 visual viewport，内容区独立滚动。
- Back 键先关闭 sheet；焦点循环、Esc、关闭后归还焦点沿用现有 Modal 无障碍契约。
- 助手挂件默认避开底栏、safe-area、键盘和当前 composer；若当前页面已有输入 composer，助手不得盖住它。
- 助手面板宽度不超过 `calc(100vw - 16px)`，高度不超过当前可视高度减去顶/底安全区。
- 任何 fixed 浮层都必须有“当前层级、关闭方式、可恢复状态”，不能只靠坐标计算。

## 7. 第一性原理：从底层约束推导 UI

### 7.1 可用高度方程

手机不是一个固定的 `100vh` 矩形。页面真正可用的高度为：

```text
H_content
= H_visualViewport
- H_topbar
- H_bottomNav
- H_safeTop
- H_safeBottom
- H_keyboardInset
- M_content
```

其中 `M_content` 至少为 16px。推论：

- 任何 fixed/sticky composer 的底边必须满足 `bottom ≥ H_bottomNav + H_safeBottom + H_keyboardInset`；
- 任何 Modal/Sheet 的最大高度必须基于 `H_visualViewport`，而不是只看布局视口 `H_layoutViewport`；
- 如果一个页面需要“猜” `bottom-20` 才不挡底栏，说明几何契约没有建立。

### 7.2 可用宽度方程

```text
W_content
= W_viewport
- P_left
- P_right
- H_safeLeft
- H_safeRight
```

必须满足：

```text
scrollWidth(document) ≤ W_viewport
```

若需要横向滚动，滚动区域必须是明确的局部内容容器，而不能是整个页面。

### 7.3 任务成功率分解

移动 UI 的最终目标不是“看起来整齐”，而是任务完成：

```text
P_task
= P_discover
× P_reach
× P_understand
× P_act
× P_recover
```

- `P_discover`：能否发现入口；
- `P_reach`：能否在一手操作下触达；
- `P_understand`：文案和层级是否让人知道下一步；
- `P_act`：命中盒、键盘和可视区是否允许操作；
- `P_recover`：失败、取消、返回、刷新后能否继续。

任何一个乘数接近 0，增加阴影、动效或缩小字体都不能补救。

### 7.4 移动端效用启发式

```text
U_mobile
= (D × R × A × E)
/ (C + W + O + F)
```

- `D`：发现性；
- `R`：可读性；
- `A`：可达性；
- `E`：可恢复性；
- `C`：认知负荷；
- `W`：等待成本；
- `O`：遮挡/溢出；
- `F`：误触和错误成本。

本阶段优先减少 `O/F/C`，而不是先增加装饰。

### 7.5 语义不变性

```text
State_mobile = State_desktop
```

更具体地说：

```text
Data_mobile = Data_desktop
AI_semantics_mobile = AI_semantics_desktop
PrimaryActions_mobile ⊇ PrimaryActions_desktop 的主任务子集
```

移动端可以隐藏、折叠、重排，但不能产生另一套数据真相、另一套评分规则或另一套圆桌语义。

### 7.6 屏幕纪律

```text
PrimaryActionPerViewport ≤ 1
```

这不是“每页只能有一个按钮”，而是每个视口只给一个明确的优先级；其他动作要么降级为次要按钮，要么进入折叠/Sheet。

## 8. 对抗式方程与攻击面

### 8.1 最弱链路原则

```text
Q_release = min(Q_successPath, Q_failureRecovery)
```

成功路径 100 分、失败恢复 0 分，发布质量仍为 0。移动端验收必须同时攻击正常路径和失败路径。

### 8.2 总阻断风险

定义每个关键失败为 0/1：

```text
F_mobile = max(
  F_keyboard,
  F_navOverlap,
  F_horizontalOverflow,
  F_hiddenAction,
  F_modalTrap,
  F_duplicateWrite,
  F_lateWrite,
  F_dataLoss,
  F_falseSuccess
)
```

只要任一关键项为 1，移动端发布结论为 `BLOCKED`，不能用其他页面通过来抵消。

### 8.3 预期伤害排序

```text
E[H_i] = P_i × Impact_i × Exposure_i
```

优先修复满足以下特征的问题：

- 发生概率高；
- 影响不可逆（删除、注销、错误覆盖、错误判通过）；
- 暴露在主流程或高频输入场景；
- 用户无法自行恢复。

因此，键盘遮挡、底栏遮挡、流式取消后 late-write、误删和同步覆盖优先于圆角、阴影和动效。

### 8.4 不可逆动作误触成本

```text
C_accidental = P_mistap × Impact_irreversible
```

当动作是删除目标、删除笔记、注销、清空数据或强制跳过时，必须同时满足：

- 命中盒 ≥44px；
- 主操作和危险操作至少 8px 分离；
- 二次确认说明后果；
- 失败或取消后不改变数据；
- 自动化和真实设备各有证据。

### 8.5 等待与取消纪律

```text
T_cancel ≤ 1s
LateWrite_after_cancel = 0
```

圆桌、教练、读书流式请求在用户切页、锁屏、键盘收起或点击停止后，不能继续把增量写入错误会话。

### 8.6 攻击矩阵

| 攻击 | 预期失败 | 通过条件 |
|---|---|---|
| 320px + 超长标题 | 标题撑破/按钮被挤走 | 标题换行或截断，主动作仍可点 |
| 横屏 667×375 | 底栏遮住 composer | 输入、发送、停止仍在 visual viewport 内 |
| iOS 刘海 | 顶/底栏贴边 | safe-area 有效，内容不被切掉 |
| Android 键盘 | 输入框和发送按钮被遮 | focused input 与动作均可见 |
| 慢网/LLM 挂起 | 页面永久 busy | 有阶段、进度、停止、重试或诚实失败 |
| 快速双击 | 重复发送/重复写入 | 一次动作只生成一条语义结果 |
| 切会话 | 旧流写入新会话 | runId 隔离，旧流不可 late-write |
| 浏览器 Back | sheet 状态残留 | 先关 sheet，再退页面 |
| 200% 字体 | 文本重叠/按钮裁切 | 信息仍可读，主动作可达 |
| hover-only 删除 | 手机上找不到功能 | 删除入口可发现，且有确认 |
| 长笔记/长表格 | 整页横向滚动 | 仅局部容器滚动，正文不被截断 |
| 刷新/换设备 | 空快照覆盖真实数据 | 移动端不改变既有同步保护纪律 |
| Demo/真实模式切换 | 语义不一致 | 同形状结果、明确标记、无假事实 |

## 13. 当前结论

移动端适配的核心不是“把所有东西塞进手机”，而是建立一条优先级明确、几何可计算、失败可恢复的学习路径：

```text
先看见下一步
→ 在安全视口内触达
→ 用最少认知负担完成
→ 失败时保留输入和状态
→ 取消后不再写错
→ 移动端与桌面端共享同一份资产
```

如果不能证明这条链路，增加更多动效、更多卡片或更多入口，只会把问题藏得更深。
