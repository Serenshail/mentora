# Mentora 回答质量、执行过程与滚动体验 PRD

日期：2026-11-15；交付复核：2026-11-16。版本：1.0，执行基线稿。任务为文档设计与交接，本轮没有修改产品代码、运行付费模型评测或部署。

这份规格解决三个可见结果：回答达到教学样例要求；回答前与执行中能看到有依据的过程；首页发送后准确回到该会话底部。最终由原主智能体根据独立证据复核，不由实现者自行宣布通过。

## 交接阅读顺序

1. `PRD.md`：需求、边界、状态与性能规则。
2. `REFERENCE-AND-DIAGNOSIS.md`：参考源码、Mentora 证据和待验证假设。
3. `EXECUTION-AND-ACCEPTANCE.md`：实施顺序、文件范围、评分、成本闸门、交付与独立验收。
4. `ACCEPTANCE.csv`：可逐项执行的产品场景，初态全部 NOT_RUN。
5. `QUALITY-CASES.json`：冻结的 30 条质量测试输入与逐条判据。
6. `HANDOFF.md`：可直接交给子智能体的执行指令。

`sources/teaching-reference.txt` 保留用户原始样例；`sources/previous-quality-cases.json` 保留既有八题原件。`source-manifest.json` 固定本地源码哈希与参考项目提交。旧文档与旧评测不覆盖、不改标。

用户所说“目前约达到 50%”登记为主观体验反馈，不伪造为已测基线；本包中的 90 分/90% 是具体测试集门槛，不是“达到某模型 90% 智能”的承诺。当前截图尚未收到，不假定已经复现用户所见的每个画面；执行者可先用源码和固定场景复现，不以等待截图替代推进。

既有 2026-11-11 体验 PRD 已涉及相同问题。本包接续其实现与复核结果，针对 11 月 15 日新增反馈重新冻结验收；这不是把过去的规划当成已经实现。本地源码有大量未提交变更，必须以文件哈希识别基线，不能只记录 HEAD。
