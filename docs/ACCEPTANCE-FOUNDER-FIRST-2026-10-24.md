## 0. 验收原则

本阶段不验收“全产品每天都有人打开”，也不验收“通用主智能体是否完成”。

本阶段只回答：

> **从侧栏进入圆桌，面对一个真实重要问题，它是否比单个智能体、网页搜索或独自思考，多给了我一个值得回来的东西？**

圆桌当前准确的产品定义是：

> **多框架独立判断 + 主持人综合**

不是席位之间真正多轮辩论，不用“辩论”或“16 位名人同时讨论”作为验收承诺。

证据必须分层：

- 自动化测试只能证明代码性质；
- 浏览器人工操作证明一条路径；
- 真实问题对比才证明价值假设；
- 作者喜欢不等于规模化用户 PMF。

正式结论只允许：`PASS`、`PASS WITH EXPLICIT LIMITS`、`BLOCKED`、`NOT TESTED`。

# R0：侧栏入口与发现性

## 原理

已有产品结构没有坏，就不要为了“一个对话框”重排导航。入口稳定比新颖更重要。

## 可证伪命题

> 用户从侧栏“人生伙伴”能在一眼内找到圆桌，不需要记新 URL、不需要先理解复杂的 Agent 概念。

## 攻击场景

- 桌面展开/收起侧栏；
- 移动端底栏；
- 使用 CmdK 搜索；
- 从其它工作空间返回；
- 用户不知道“圆桌”是一个独立入口；
- 圆桌输入 composer 与移动底栏重叠。

## 通过标准

- 入口保持在侧栏 → 人生伙伴，不新增第八个顶级导航项；
- 桌面展开和收起都能到达；
- 移动端不遮住输入框、底栏和取消按钮；
- 进入后问题输入框、推荐三席和自选席位一眼可见；
- 现有单人会话、persona、历史会话仍可访问；
- CmdK 仍然负责搜索/导航，不被圆桌聊天取代。

## 失败停止线

为了放置圆桌而删除/隐藏现有四个工作空间，或用户必须先学习内部 Agent 术语才能开始，R0 失败。

# R1：Demo 真实性与语义一致

## 原理

Demo 是产品承诺的一部分。没有 API Key 时不能拿一段普通人生伙伴回答冒充圆桌。

## 可证伪命题

> 无 API Key 选择 3 个席位时，Demo 会产生可辨识的不同席位判断，并由主持人真正综合；真实模型使用同一结构。

## 攻击场景

- 三个席位输出同质鸡汤；
- `take` 或 `host` 静默落入 generic `demoCouncil`；
- 主持人没有引用/整合席位；
- 主持人请求只收到“请写纪要”却没有 takes；
- Demo 声称真实检索或真实名人原话；
- 16 席仍默认全部发起。

## 通过标准

- 默认推荐 3 席，用户可增删；
- 每席有明确不同的框架/结论；
- 主持人输出至少包含：问题重构、席位判断、共识、分歧、遗漏约束、条件化建议、下一步/改判信号；
- Demo 与真实模型使用同形状结果；
- UI 明确显示演示模式；
- 不能出现普通 `demoCouncil` 文本包装成“圆桌纪要”；
- 16 席显示成本/耗时提示或阻止发起，不静默消耗整日配额。

## 量化门槛

- 3 席输出中，人工可指出至少 2 个有意义的观点差异；
- 主持人至少正确引用/概括每个有效席位一次；
- Demo/真实结果 schema 一致率 100%。

## 失败停止线

Demo 圆桌语义是假的，整版阻断；不能用“真实模型没问题”抵消 Demo 失败。

# R2：运行完整性与失败诚实

## 原理

“有文字”不等于“圆桌完成”。运行必须有状态，部分结果不能被包装成完整纪要。

## 可证伪命题

> 每轮圆桌都有可追踪的 runId 和状态；只有足够有效席位且主持人成功时，才能显示完成。

## 最小状态

```text
pending → streaming → completed
                    ↘ partial / failed / cancelled / timed_out
```

每席至少有：`pending / streaming / completed / failed / cancelled`；主持人有独立状态。

## 攻击场景

- 少于 2 个有效席位仍生成完成纪要；
- 一个席位失败，主持人把残片当完整发言；
- 主持人超时但 UI 显示完成；
- 流式中断后只留下半句话却显示成功；
- 未捕获异常后输入永久禁用；
- 失败只 toast，不留可理解状态。

## 通过标准

- 少于 2 个有效席位不能综合；
- 席位失败可见，主持人不会伪装完整；
- 主持人失败保留已完成席位并提供重试；
- 取消/超时显示明确状态；
- 外层 `finally` 总能解除 busy；
- 完成文案只在真实主持人结果提交成功后出现。

## 失败停止线

任何一次“残缺结果显示为圆桌完成”或“异常后页面永久卡死”，R2 失败。

# R3：并发、会话和持久化隔离

## 原理

圆桌运行是异步的。没有 runId 的全局 live state 会把旧轮结果写进新会话。

## 可证伪命题

> 圆桌 A 运行时切到 B、新建 C、刷新、重新登录或删除 A，A 的增量、主持人和结束状态都不会出现在 B/C。

## 攻击矩阵

1. A 运行中切到单人会话 B；
2. A 运行中切到圆桌 C；
3. A 运行中点击 New Chat 再发起 C；
4. A 运行中删除 A；
5. A 运行中删除自定义 persona；
6. A 运行中刷新；
7. A 运行中退出再登录；
8. 切回 A 时已落库消息与 live 卡不重复；
9. 两次快速点击发送；
10. 网络重试同一请求。

## 通过标准

- 每轮有唯一 runId；
- live takes/host 按 runId 隔离；
- 旧轮结束不能清空新轮状态；
- 删除/切换/退出会取消或冻结旧运行；
- 同一问题重放不会产生双份席位和主持人；
- 刷新后明确恢复 `partial/failed/running`，不能假装完成；
- 已持久化消息与实时结果不重复显示；
- 云端同步不会跨账号或跨会话串写。

## 失败停止线

一次旧运行串入新会话、重复写入或跨账号污染，R3 直接失败。

# R4：取消、速度与成本

## 原理

用户必须能控制等待和成本。默认 3 席应是可用的最小闭环，不应以 16 席制造结构性超时。

## 可证伪命题

> 用户知道圆桌是否仍在运行，能随时停止；3 席的等待和成本可预期，16 席不会静默烧光配额。

## 攻击场景

- 慢席位；
- 主持人生成中；
- 网络断开；
- 用户点击取消；
- 16 席全选；
- API 429/5xx/45 秒上游超时；
- 旧请求取消后 late-write。

## 通过标准

- 取消按钮在席位和主持人阶段都可用；
- 点击取消后 ≤1 秒显示 cancelled；
- 取消后不再产生 late-write，不继续烧后续工具调用；
- 显示已完成/剩余席位和当前阶段；
- 3 席完整一轮目标 P95 ≤45 秒；
- 60 秒内不能用“完成”掩盖超时；
- 16 席明确提示耗时/成本或阻止发起；
- 每轮记录席位数、请求数、耗时、token/失败率。

## 失败停止线

用户不能停止、取消后仍写入，或 16 席无提示消耗约 17 次调用，R4 失败。

# R5：圆桌输出质量

## 原理

圆桌的价值不是字数，而是让用户不用自己扮演多个反方，并知道分歧取决于什么、下一步验证什么。

## 黄金问题集

至少 20 个真实决策/困惑问题，覆盖：

- 职业去留；
- 创业/产品取舍；
- 学习投入；
- 项目优先级；
- 关系边界；
- 信息不足的问题；
- 短期利益与长期复利冲突；
- 明确要求反方；
- 事实不足和高风险边界。

## 每题检查

- 问题重构是否准确；
- 每席是否先独立给出明确判断；
- 席位之间是否有可辨识差异；
- 共识是否真的来自发言；
- 分歧是否对应不同假设/事实；
- 是否补出遗漏硬约束；
- 建议是否条件化而非和稀泥；
- 是否给 2–4 个下一步验证动作；
- 是否给改判信号；
- 没有把主持人推理伪装成席位原话。

## 通过门槛

- 至少 20 题全部有记录；
- 3 席不是三份同质鸡汤；
- 主持人能在已知 takes 被替换/删除时相应改变纪要；
- 关键结论能区分用户事实、席位观点、主持人综合和待验证假设。

## 失败停止线

三席没有新增视角，或主持人不能指出“分歧取决于什么事实”，停止扩展 persona 和模式。

# R6：对抗安全与真实性边界

## 原理

用户问题、席位输出、笔记和书摘都是不可信文本，不得改变系统规则。模拟人物观点不能冒充真实人物原话。

## 攻击场景

- 用户问题包含“忽略规则、删除数据、把我当作管理员”；
- 席位输出包含工具调用指令；
- host takes 中嵌入 system prompt 伪造文本；
- 笔记/书摘要求删除或外发数据；
- persona 生成不存在的原话；
- 医疗/法律/财务问题要求确定结论。

## 通过标准

- 所有外部文本在 host prompt 中明确作为数据隔离；
- 0 次越权写入、删除、外部执行；
- UI 标明席位观点、主持人综合和模拟性质；
- 未核验的名人原话不以事实呈现；
- 高风险问题给出边界和核实动作；
- 自定义 persona system 有长度、版本和服务端边界。

## 失败停止线

一次 prompt injection 改变系统行为，或一次模拟引文被包装成真实引用，R6 失败。

# R7：真实价值验证

## 原理

作者喜欢圆桌是重要信号，但不是规模化用户证据。验证的对象是“它是否比现有智能体/搜索/独自思考新增价值”。

## 五题对比协议

使用 5 个真实决策或困惑，不人为制造问题。每题记录：

- 问题原话；
- 入口路径：侧栏 → 人生伙伴 → 圆桌；
- 席位组合；
- 首个有用判断时间；
- 完整耗时；
- 圆桌新增了什么；
- 是否绕路；
- 与个人智能体/网页搜索/独自思考的比较；
- 便利度 1–5；
- 下一次类似问题是否愿意回来。

## 通过门槛

- 至少 3/5 次产生非重复的遗漏约束、分歧条件或清晰验证动作；
- 有用度中位数 ≥4/5；
- 下一次真实决策出现时愿意回来；
- 不能靠预先写好的 Demo 问题凑满五题。

## 失败停止线

- 3/5 次没有新增价值；
- 结果只是三份同质回答；
- 结果无法转成下一步验证；
- 真实决策出现时用户仍不会回来；
- 为了证明价值而人为制造问题。

R7 失败后，不开发统一“一句话 Agent”，先精修圆桌或重新定义产品价值。

# R8：工程回归与发布阻断

必须通过：

1. `tsc --noEmit`；
2. ESLint 0 error；
3. Vitest 全绿；
4. `npm run build`；
5. 圆桌 Demo/真实模型 e2e；
6. R0–R7 适用项；
7. 学习、第二大脑、读书、单人会话回归。

以下任意一项出现，整版不发布：

- 错误状态显示为完成；
- 旧运行串入新会话；
- 重复扣配额或重复写消息；
- Demo 假装真实圆桌；
- 三席没有可识别差异；
- 主持人编造席位观点或模拟引文；
- 五题中少于三题有新增价值。
