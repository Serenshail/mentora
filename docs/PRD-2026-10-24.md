# Mentora Founder-First PRD

> **版本**：Founder-First v1.0 · 2026-10-24  
> **状态**：规划中（Planned），本文不代表主智能体已经实现。  
> **适用范围**：下一阶段产品方向、首页主入口、统一智能体协议、创始人自用验收。  
> **相关验收**：[Founder-First 对抗式验收标准](ACCEPTANCE-FOUNDER-FIRST-2026-10-24.md)

---

## 0. 先做一个不讨喜但必要的判断

Mentora 现在**功能不少，但还没有成为一个我自己每天愿意打开的工具**。

这不是“再加一个功能”可以解决的问题，也不是把四个页面再做得漂亮一点就会自动解决的问题。真正的问题是：

> 我有一个真实意图时，是否可以不用先想产品结构，就从一个入口得到正确的下一步，并且在做完后留下对下一次有用的东西？

如果答案是否定的，继续增加 persona、阅读模式、图谱按钮或更多提示词，只会让产品更完整，却不会让它更好用。

**本 PRD 的第一原则：创始人是第一个用户。**

在创始人没有连续使用、没有主动回到产品、没有真实留下资产之前：

- 不以注册人数证明产品成立；
- 不以 demo 演示顺滑证明产品成立；
- 不以“功能已经做出来”证明产品成立；
- 不进入增长、收费、复杂自动化或更多功能扩张。

## 1. 当前产品基线：什么已经存在，什么还没有

### 1.1 已存在且应保留的能力

Mentora 当前已有四个成熟工作空间：

1. **学习教练**：引导 → 目标 → 两级计划 → 每日讲义 → 验收门 → 迁移题 → FSRS 复习 → 掌握状态。
2. **第二大脑**：Obsidian 式笔记、`[[双链]]`、反向链接、图谱、标签、MOC、AI 建联、LLMWiki、BM25/RAG。
3. **读书伙伴**：书籍档案、非目录式阅读路线、五种对话模式、三重验收、洞见入库。
4. **人生伙伴**：反迎合纪律、内置 persona、自定义 persona、单人会话、圆桌纪要。

工程层已有可复用底盘：

- `/api/chat` 统一 AI 入口；
- `ChatTask` 显式任务路由；
- 服务端组装核心 prompt，客户端主要发送结构化 `args`；
- NDJSON 流式输出、超时、重试、取消、BYOK、服务端模型、Demo 模式；
- Zustand 本地状态 + 云端全量快照同步；
- Zod 产物 schema；
- FSRS、掌握状态机、回归测试与 CI 门禁。

这些都是资产，不推倒重来。

### 1.2 当前真实缺口

首页仍然是一个仪表盘：用户需要先理解“学习教练 / 第二大脑 / 读书伙伴 / 人生伙伴”的信息架构，再选择入口。

全局 `AssistantWidget` 目前只是**产品使用问答挂件**：它能回答“功能在哪、怎么用”，但不能可靠地：

- 从自然语言识别用户意图；
- 查询统一的工作空间上下文；
- 在四个能力之间路由；
- 生成可确认的目标/笔记/洞见提案；
- 以统一动作协议写入数据；
- 把一次对话变成可追踪、可复用、可撤销的认知资产。

当前更准确的描述是：

> Mentora 有四个能力插件和一个问答挂件，还没有一个真正的主智能体。

### 1.3 本阶段不假装已完成的事项

以下均为规划项，不是当前现状：

- 首页主对话入口；
- 统一意图识别层；
- 工具调用与审批事件；
- 目标/笔记/洞见的统一提案卡；
- Decision / ActionItem 结构化模型；
- Agent run 审计、幂等与回放；
- Founder-First 7 天真实使用通过；
- 对抗式黄金测试集达到指标。

## 2. 第一性原理：产品到底在交付什么

### 2.1 从聊天表面还原价值链

一个学习/思考产品的最小价值链不是：

> 输入问题 → 输出一段文字

而是：

> **意图 → 正确理解 → 下一步行动 → 可验证结果 → 持久资产 → 下次更容易**

这六个环节中任何一个断裂，产品就可能变成“看起来聪明、实际上增加认知负担”的聊天工具。

| 环节 | 产品必须回答的问题 | 失败表现 |
|---|---|---|
| 意图 | 用户此刻真正想完成什么？ | 把“帮我记下来”当成普通问答 |
| 理解 | 系统理解了哪些事实？做了哪些假设？ | 用户要反复纠正 AI |
| 行动 | 下一步是什么？谁来做？ | 输出一大段话但没有动作 |
| 结果 | 如何判断动作真的完成？ | AI 说“已完成”，实际没写入 |
| 资产 | 本次交互留下什么？ | 第二天重新解释同一件事 |
| 复利 | 下次是否因此更快、更准？ | 每次聊天都从零开始 |

### 2.2 五条第一性原理

**原理一：用户不应该学习产品的信息架构。**  
用户应该说“我想学 Python”“把这个记下来”“我今天该做什么”，而不是先判断自己要进入哪个模块。

**原理二：聊天是入口，不是产品本身。**  
对话负责理解和编排；结构化页面负责长期操作、检查和回看。不能用聊天气泡替代学习计划、笔记编辑器和复习队列。

**原理三：模型负责概率判断，代码负责事实和状态。**  
模型可以猜意图、提出计划、生成草稿；模型不能凭自然语言直接解锁学习日、删除笔记、覆盖计划或声称写入成功。

**原理四：每次交互必须有明确结果类型。**  
一次对话最终只能落到三类结果之一：

1. 已执行的低风险动作；
2. 等待用户确认的结构化提案；
3. 明确说明当前无需行动或无法可靠行动。

“生成一段漂亮长文”不是第四类完成状态。

**原理五：真正的护城河是用户资产的复利。**  
一次回答会消失；目标、笔记、双链、复习记录、决策和行动项会积累。Mentora 必须把对话导向用户自己的资产，而不是把用户留在无限聊天里。

### 2.3 反命题：每个主张都要能被推翻

| 产品主张 | 必须接受的反例 | 不能通过的条件 |
|---|---|---|
| “一个入口更简单” | 用户不知道当前正在做什么或找不到旧内容 | 入口变简单、结果变模糊 |
| “AI 能自动帮我做” | 模型误判、重复执行、越权、覆盖数据 | 没有确认和幂等保护 |
| “聊天更自然” | 用户说完后仍需手动找页面、复制内容、重建状态 | 聊天增加了绕路 |
| “功能越多越强” | 创始人每天只用不到一个主路径 | 功能存在但没有重复使用 |
| “Demo 很顺” | 真实笔记、真实目标、真实失败、断网和旧数据进入后崩溃 | 只在干净数据上通过 |
| “AI 懂我” | 用户必须不断纠正假设，或 AI 把模拟观点当事实 | 两次连续误解同一意图 |

**产品决策只能在正例和反例同时通过时成立。**

## 3. 产品形态：一个入口，不是一个窗口

### 3.1 结论

采用：

> **一个入口、一个主智能体、四个工作空间、一个持续增长的个人认知资产库。**

不采用：

> 只有一个空白聊天框，所有功能都隐藏在无限对话里。

### 3.2 首页形态

首页第一屏应同时具备三层：

```text
继续。

[告诉我你现在想学什么、整理什么、读懂什么，或正在纠结什么……]

[开始学习] [安排今天] [整理笔记] [继续读书] [帮我做决定]

今天
├── 当前学习日
├── 到期复习
└── 当前阅读
```

原则：

- 对话是第一入口；
- 今日状态仍然可见，不藏在对话里；
- 快捷按钮是示例和低认知成本入口，不是新的菜单墙；
- 侧栏和四个工作空间保留；
- 用户可以随时从对话跳到结构化页面；
- 页面返回后，智能体知道刚才做到了哪一步。

### 3.3 主智能体职责

主智能体 `Mentora` 负责：

1. 识别用户当前意图；
2. 读取最小必要的工作空间上下文；
3. 选择一个能力或一组有序能力；
4. 解释假设与下一步；
5. 生成提案或发起低风险动作；
6. 在需要时请求确认；
7. 通过确定性执行层提交动作；
8. 返回真实结果、位置、状态和后续路径。

主智能体不负责：

- 取代学习页面；
- 取代第二大脑编辑器；
- 取代复习判分状态机；
- 直接操作 Zustand state；
- 代替用户做不可逆决定；
- 把所有能力写成一个超长 system prompt。

### 3.4 四个工作空间的定位

| 工作空间 | 主智能体能做什么 | 最终操作在哪里完成 |
|---|---|---|
| 学习教练 | 识别学习目标、展示当前任务、生成目标/计划提案 | `/learn` 与目标详情页 |
| 第二大脑 | 搜索、引用、生成笔记/双链提案 | `/brain` 工作台 |
| 读书伙伴 | 打开书、生成阅读路线提案、保存洞见 | `/read` 与书籍详情页 |
| 人生伙伴 | 给判断、反方、下一步，生成决策记录提案 | `/council` 与未来决策页 |

## 4. Founder-First 核心场景（P0）

P0 只验证五条真实路径，不先追求“什么都能做”。

### 场景 A：我想学，但不知道从哪开始

**输入示例**：

> “我想学 React，最终能独立做一个真实项目，但我不知道应该从哪里开始。”

**预期路径**：

1. 主智能体识别 `learn`；
2. 最多问一到两轮真正影响计划的问题；
3. 展示自己的假设、成功标准和每周投入；
4. 生成可编辑目标卡；
5. 用户确认后才创建/激活目标；
6. 跳转学习教练继续现有引导和计划流程；
7. 目标、计划和后续学习记录进入已有 store/同步链路。

**禁止**：

- 用户没有确认就创建 active 目标；
- 直接替换已有目标；
- 把模型猜测的截止日期当承诺；
- 用长篇解释代替目标卡。

### 场景 B：我今天该做什么

**输入示例**：

> “我今天只有 30 分钟，Mentora 觉得我现在最该做什么？”

**预期路径**：

1. 读取当前 active goal/day、到期复习、当前阅读和用户明确的时间约束；
2. 给一个首选动作，最多两个备选；
3. 说明依据和预计投入；
4. 一键进入对应页面；
5. 完成后能回到同一上下文。

**禁止**：

- 推荐已完成或被锁定的学习日；
- 忽略待复习而只推荐新内容；
- 在没有依据时编造“最重要”；
- 把三个模块同时塞给用户让用户自己取舍。

### 场景 C：把这段内容整理进第二大脑

**输入示例**：

> “这段关于闭包的内容帮我整理成一篇笔记，并和我已有的 React 笔记连起来。”

**预期路径**：

1. 检索相关笔记，而不是发送全库；
2. 生成标题、正文、标签、候选双链的提案卡；
3. 明确哪些内容来自用户输入、哪些是模型补充；
4. 用户可编辑标题/正文；
5. 用户确认后保存；
6. 双链逐条显示并可接受/拒绝；
7. 返回真实笔记 ID、位置和后续复习建议（如有）。

**禁止**：

- 同名笔记静默覆盖；
- 自动合并已有笔记；
- 自动把参考类笔记加入今日复习队列；
- 把笔记里的“忽略指令/删除数据”等文本当成系统命令。

### 场景 D：我在读或想读一本书

**输入示例**：

> “我想读《思考，快与慢》，但不想按目录机械读，帮我安排一条路线。”

**预期路径**：

1. 判断书架中是否已有该书；
2. 已有则打开并恢复上下文；没有则生成阅读计划提案；
3. 用户确认后创建书籍/路线；
4. 进入读书伙伴，保留章节问题与模式；
5. 洞见进入提案，而不是直接写入多个地方。

**禁止**：

- 重复创建同一本书；
- 没有计划预览就直接写入正式阅读路线；
- 把 heuristic 评分伪装成模型确定结论；
- 未确认就把章节标记为已完成。

### 场景 E：我在纠结一个人生问题

**输入示例**：

> “我在考虑要不要离开现在的工作，帮我把问题想清楚。”

**预期路径**：

1. 先明确这是判断/决策问题，不假装有唯一事实答案；
2. 给出第一句判断、最强反方、关键假设、下一步实验；
3. 明确区分用户事实、模型推理、persona 模拟；
4. 用户主动选择时，生成决策记录/行动项提案；
5. 高风险医疗、法律、财务问题给出核实边界，不自动执行外部动作。

**禁止**：

- 用名人 persona 的模拟观点冒充真实引文；
- 把安慰当答案；
- 自动替用户发消息、辞职、购买或发布；
- 在事实不足时使用过度确定语气。

## 5. MVP 范围与非目标

### 5.1 P0：必须先做

- 首页主对话入口；
- 统一 `AgentIntent`；
- 最小 `WorkspaceContext`；
- 只读工具：当前目标、今日任务、待复习、当前书、第二大脑检索、功能帮助；
- 目标卡、笔记、洞见、阅读路线提案卡；
- 用户确认后调用确定性 store action；
- 页面导航和结果回写；
- Demo/真实模型同形状；
- 50 条以上意图黄金测试集；
- 运行 ID、动作 ID、错误和取消可观测。

### 5.2 P1：P0 通过后再做

- 学习计划 patch 提案（已有进度时禁止整体覆盖）；
- 双链/冲突/LLMWiki 提案统一化；
- Decision / ActionItem 模型；
- 软删除、回收站、撤销；
- 跨模块行动列表；
- Agent run 回放和审计页；
- 多轮任务恢复。

### 5.3 明确不做

- 只有聊天、隐藏所有结构化页面；
- 让一个超长 prompt 取代业务状态机；
- LLM 直接调用 Zustand mutation；
- 自动删除、自动覆盖、自动合并；
- 自动替换已有学习计划；
- 自动外部执行（发信、日历、购买、发布、财务）；
- 原生 App；
- 在创始人首用验证前扩展更多 persona、模式或增长功能。

## 6. 技术与协议要求（规划）

### 6.1 复用现有底盘

复用而不是重写：

- `/api/chat`；
- `streamChat` / `useChat`；
- `ChatTask` 与现有 task router；
- 服务端 `buildSystem` 和 `server-only` prompt 边界；
- BYOK、服务端模型、Demo 三通道；
- 现有 Zod 产物 schema；
- store action、FSRS、掌握状态机、RAG、Wiki 编译。

### 6.2 新增概念

```ts
 type AgentIntent =
   | "learn"
   | "review"
   | "brain"
   | "reading"
   | "life"
   | "app-help"
   | "mixed"
   | "unknown";
```

规划中的结构化对象：

- `WorkspaceContext`：当前路由、当前目标/日、待复习摘要、当前书、有限检索结果、能力清单；
- `AgentRun`：`runId`、用户、intent、prompt/version、开始/结束、状态、预算、错误；
- `ToolCall` / `ToolResult`：名称、schema、风险、参数摘要、结果、耗时；
- `ApprovalRequest`：动作、影响对象、diff、假设、撤回方式、过期时间；
- `ActionEnvelope`：`actionId`、幂等键、actor、kind、riskLevel、targetIds、payload、expectedVersion、确认时间、结果。

### 6.3 事件协议

保持旧事件兼容：

```json
{"t":"d","v":"文本增量"}
{"t":"e","v":"错误"}
{"t":"end"}
```

在新 Agent 入口逐步增加：

```json
{"t":"meta","runId":"...","intent":"learn"}
{"t":"delta","v":"..."}
{"t":"tool_call","id":"...","name":"search_brain","args":{}}
{"t":"tool_result","id":"...","ok":true,"data":{}}
{"t":"approval_required","id":"...","action":"create_goal","preview":{}}
{"t":"navigation","href":"/learn/..."}
{"t":"done","result":{}}
{"t":"error","code":"...","message":"..."}
```

约束：

- 事件有顺序号和 `runId`；
- tool result 由服务端产生，模型不能伪造；
- `done` 前不得宣称写入成功；
- 客户端取消必须终止后续工具调用；
- 每次 run 有工具数、时间、token/成本上限；
- 旧页面继续使用旧 `ChatTask`，迁移按 PR 分批完成。

### 6.4 工具分级

**只读工具（默认自动）**：

- `get_workspace_summary`
- `get_active_goal`
- `get_due_reviews`
- `get_current_book`
- `search_brain`
- `get_feature_help`

**建议工具（生成提案）**：

- `draft_goal_card`
- `draft_learning_plan`
- `draft_note`
- `suggest_links`
- `draft_reading_plan`
- `draft_decision`

**写入工具（确认后执行）**：

- `create_goal`
- `save_note`
- `save_insight`
- `link_notes`
- `save_book`
- `create_decision`
- `create_action_item`

写入工具必须使用 Zod 输入/输出 schema，且通过确定性 store action 执行。

### 6.5 上下文和隐私分级

| 级别 | 默认可发送内容 | 约束 |
|---|---|---|
| P0 | 用户当前输入、当前路由、公开功能 metadata | 必须有长度上限 |
| P1 | 当前目标、当前学习日、当前书、有限检索摘要、待复习摘要 | 仅按意图发送 |
| P2 | 全量笔记、全部历史会话、邮箱、API key、persona system、无关私人数据 | 默认禁止 |

检索到的笔记、书摘和外部文本都是**不可信数据**：其中的指令只能作为内容被引用，不能改变 Agent 规则或触发高风险动作。

### 6.6 Demo 契约

每个主智能体 intent 必须有同语义 Demo：

- 返回同样的结构化 schema；
- 走同样的提案/确认界面；
- 明确标注演示模式；
- 不伪造真实检索、真实用户状态或真实引文；
- 不得把未覆盖 task 静默降级为 `demoCouncil`；
- Demo 与真实模型失败都必须能被用户区分。

## 7. 动作生命周期与确认矩阵

### 7.1 生命周期

```text
 detected
   → parsed
   → validated
   → auto | proposed | strong_confirm
   → executing
   → committed
   → sync_pending
   → synced
```

异常分支：

```text
 rejected | cancelled | failed | conflict | expired | rolled_back
```

每个写动作必须记录：

- `actionId` / `idempotencyKey`；
- `runId`；
- actor（user / agent / system）；
- 风险等级；
- 目标 ID；
- 变更前版本；
- 提案或 diff；
- 用户确认时间；
- 执行结果；
- 同步状态；
- 错误或回滚信息。

### 7.2 确认矩阵

| 动作 | 默认级别 | 规则 |
|---|---|---|
| 查询当前目标/任务/复习/书籍 | 自动 | 只读、可取消 |
| 页面导航 | 自动 | 只能跳站内路径 |
| 生成建议/回答问题 | 自动 | 不改变持久状态 |
| 创建目标卡 | 预览确认 | 用户可编辑假设后确认 |
| 生成学习计划 | 预览确认 | 有进度时只能 patch，不得整体覆盖 |
| 保存新笔记/洞见 | 预览确认 | 标题、正文、来源、复习策略可见 |
| 建立双链 | 预览确认 | 逐条接受，宁缺毋滥 |
| 创建书籍/阅读路线 | 预览确认 | 防重复、显示影响对象 |
| 生成决策/行动项 | 预览确认 | 事实、推理、模拟观点分层 |
| 修改已有笔记 | 强确认或 diff 确认 | 显示前后差异，可回退 |
| 删除/覆盖/合并 | 强确认 | 二次确认，默认不可自动执行 |
| 跳过学习验收/绕过读书验收 | 强确认 | 保留理由和审计记录 |
| 注销/清空数据/外部副作用 | 强确认 | 二次确认、影响范围、不可逆提示 |

### 7.3 当前业务状态必须继续由代码掌控

- 学习验收和迁移题门不能被 Agent 绕过；
- FSRS 和掌握状态不能由自然语言直接推进；
- Wiki 合并不能自动删除原笔记；
- 同名笔记不能静默覆盖；
- 删除目标的级联范围必须显式展示；
- 任何“已完成”文案必须在真实 mutation 成功后出现。

## 8. 创始人使用指标与停止线

### 8.1 7 天真实使用协议

在真实数据、真实时间和真实任务上完成：

- 至少 10 个真实任务；
- 至少 5 个不同日期使用；
- 至少覆盖学习、第二大脑、读书/人生中的三类路径；
- 至少 3 次把结果沉淀成目标、笔记、洞见或行动项；
- 至少 1 次遇到失败、取消、模糊输入或中途改变意图；
- 记录输入、路由、澄清轮数、耗时、结果、资产、绕路次数、主观便利度（1–5）和“明天是否愿意再打开”。

### 8.2 P0 体验指标

| 指标 | 目标 |
|---|---:|
| 首屏进入主入口并可输入 | ≤ 3 秒（本地/正常网络） |
| 常见意图正确路由 | 黄金集 Top-1 ≥ 90% |
| 从输入到可执行下一步 | ≤ 2 轮澄清 |
| 提案卡理解“改什么/改哪里/如何撤回” | ≤ 5 秒读懂 |
| 未确认高风险 mutation | 0 |
| 重放/双击重复写入 | 0 |
| 真实任务留下可复用资产 | ≥ 60% |
| 创始人主观便利度中位数 | ≥ 4/5 |
| 创始人 7 天内主动回访 | ≥ 5 天 |

### 8.3 停止线

以下任意一项失败，停止增加功能，回到入口、理解、动作和结果链修复：

- 连续两次把明确意图路由到错误能力；
- 用户需要先打开侧栏寻找功能；
- 低置信度输入直接触发写入；
- AI 宣称完成但真实数据未改变；
- 未确认就删除、覆盖、跳过或替换；
- 同一个 action 重放造成第二次写入；
- 旧响应覆盖新编辑或跨账号串仓；
- 7 天便利度中位数低于 4/5；
- 创始人第 7 天仍不愿意再次打开产品。

## 9. 分阶段实施顺序

### PR 1：协议先行

- 新增 Agent 类型、意图 schema、ActionEnvelope、事件 schema；
- 新增 50 条意图黄金集和结构化失败用例；
- 不改变现有页面行为；
- 通过 Gate 1/2 的自动化部分后再继续。

### PR 2：只读主入口

- 首页主对话 UI；
- WorkspaceContext；
- 只读工具；
- 页面导航；
- 先证明“问一句能找到正确东西”，不做写入。

### PR 3：提案和确认

- 目标卡、笔记、洞见、阅读路线提案；
- 统一预览/确认/取消/过期；
- 确认后调用现有 store action；
- 补幂等和写入审计。

### PR 4：跨模块资产

- 计划 patch；
- 双链提案；
- Decision / ActionItem；
- Agent run 回放；
- 处理旧请求、切账号、断线和冲突。

### PR 5：可靠性与真实使用

- Demo 同形状；
- 异常、限流、超时、取消和恢复；
- 移动端、键盘、焦点和读屏；
- 进行 7 天 Founder-First dogfooding；
- 通过全部对抗式 Gate 后才考虑增长或收费。

## 10. 发布原则

1. 先让创始人愿意用，再让别人注册。
2. 先修入口和结果链，再加能力。
3. 先建立可证伪验收，再相信 demo。
4. 先让动作可追踪、可取消、可回退，再提高自动化程度。
5. 任何 AI 链路改动仍需本地 e2e；任何纯逻辑改动必须补回归测试。
6. 任何未验证项必须写“未验证”，不以代码审查代替真实使用。

**最终产品判断标准不是“它能回答什么”，而是：**

> **我有事时会不会自然地打开它；打开后会不会更快地做成事；做完后我的系统是否变得更聪明。**
