# EVAL-01 产品行为决定

日期：2026-11-10 · 状态：本轮确定的后续实现与评测规则

先确定用户应得到什么，再调查实现。此次不修改评分器、不重算旧成绩、不改模型行为。下列规则适用于下一版评测，不能回写 v2 为通过。

## 1. 学习请求的行为边界

| 用户请求与已知上下文 | 默认行为 | 结束条件 |
|---|---|---|
| 单点解释、概念、代码问题 | 直接回答，不创建目标 | 用户问题得到回答 |
| 表达学习意愿，缺少会影响路线的目的或基础 | 先问最必要的 1–2 个问题；已经知道的信息不重复问；首轮默认不写业务数据 | 首轮记“已合理澄清”，尚未完成学习计划任务 |
| 用户明确说“先建一个目标/草稿，细节以后聊” | 直接创建草稿，保存已知信息，未知项留空或明确未定 | 草稿真实存在，背景准确，返回接续入口；不能称完整计划已完成 |
| 学习目的和约束已明确，并要求制定/调整计划 | 继续生成具体方案，不再反复询问已知条件 | 新建/编辑遵循现有具体方案与应用规则；检查真实结果 |
| 用户说“按默认安排”“你决定，先做起来” | 说明可调整的假设并推进；假设不能冒充用户事实 | 得到可继续的草稿或方案，实际保存状态准确 |
| 只是探讨是否应该学 | 讨论，不创建目标 | 给出理由和条件，不产生未要求的写入 |

“资料为空”不等于“用户零基础”；“background 非空”也不等于背景保存正确。没有用户背景时可以保留未知，不能为了通过判据编造背景文本。

## 2. in12 与 in16 的具体预期

当前 fixtures 的问题分别为：

- in12：我想学线性代数。
- in16：我想系统学 Rust。

在缺少相关上下文的初态下，两条都允许先问学习用途和已有基础，默认首轮不创建目标。in16 已表达系统学习意图，但这不等于已具备安排学习路线所需的信息。

后续评测应拆成两个阶段：

1. 首轮检查是否合理回应学习意愿、问到关键缺失信息、没有问卷式盘问、没有编造背景、没有擅自创建正式计划。
2. 提供固定的下一轮用户回复，明确用途、基础、时间和创建请求；检查能否继续完成交接，真实目标字段和入口是否正确，不能再次询问相同信息。

例：Rust 后续回复可固定为“我会 Python，想用 Rust 写命令行工具，每周 3 小时，请按这些信息建立学习目标。”这属于新测试输入，需独立编号并在运行前冻结。

首轮的合格澄清和最终任务完成分别统计，不能把只问了问题计作已完成交接。v2 中两条仍保留原检查结果，附“预期需按本决定修订”，不能直接把总分提高。

## 3. 读书请求的具体预期

in13 是“帮我好好读一遍《影响力》”，fixture 的 focus 还明确提到已有书籍应恢复而不是重复添加。因此下一步调查必须先固定书架初态：

- 已有确定的同一本书：恢复该书与当前进度，不要求调用 add_book，不重复创建。
- 书架没有该书且可明确书目：使用真实加书/核查流程，成功后进入阅读；无需仅为了形式再问一次是否愿意读。
- 书名、作者或版本影响内容且无法确定：针对缺项澄清。
- 核查或工具执行失败：如实说明具体失败与恢复办法；不能没有尝试就笼统声称“系统不能添加”。

in14 明确要求把《思考快与慢》加入书架，按上述查重与核查规则执行。空回答仍是未完成任务；应调查上游返回、流式结束、消息保存和评测器取数，不能凭猜测将其排除出分母。

## 4. 统计与版本约定

v2 的 24/30 = 80% 是整批观察到的通过率；24/28 = 85.7% 只能标为“排除已归类上游故障后的条件通过率”。上游故障仍影响用户端成功率，两者同时报告。该分类是否准确需有错误证据，不能因请求失败就默认产品无关。

单次 30 例只是本轮样本结果，不是生产成功率或稳定性保证。旧版与新版判据、样本初态和运行条件不同，不能据此宣称效果提升。

新评测在运行前冻结问题、初态、期望分支、检查项和脚本哈希；运行后发现判据问题则登记、留存旧结果，在下一版本调整。不能边跑边改当前批次判据。

## 5. 执行顺序

本轮已完成产品规则定义。接下来先调查 in13 的实际工具链与书架初态，再定位 in14 的空回答；后续按新规则补多轮用例并独立运行。计划编辑 UI 的验收仍是未完成事项，不因模型路由评分变化而改标通过。阅读与人生伙伴第二批扩展继续等待第一批验收收口。
