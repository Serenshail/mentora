## 2. 判据存在可复现的假通过

依据：产品决定 §2 要求真实目标字段和入口正确；冻结稿 §2.2 明确背景须在新目标字段中保存，不能凭回答文案判定。

| 反例 | 实际输入事实 | 当前判定 | 根因 |
|---|---|---|---|
| F1 | 新目标 background 为空，回答复述了全部背景 | PASS，backgroundSaved=true | eval-scoring-v2.mjs:148 的 `bg.includes(p) || text.includes(p)` 允许正文代替保存证据 |
| F1b | 根本没有读取到 goal 对象，只有数量增量和成功文案 | PASS | 同上；没有要求有效的目标对象 |
| F2 | 创建 g1，返回链接指向 not-g1 | PASS，hasEntry=true | :158 只匹配 URL 前缀或“继续引导”等词，不核对目标 ID |
| F3 | 回答“用途和基础以后再说。”，没有提出任何澄清请求 | PASS，clarifyRelevant=true | :120 命中“用途/基础”等关键词便视为澄清 |
| F4 | 加书工具失败，所有对象增量为 0；存在旧目标背景 | PASS，handoffHappened=true | :75 仍以工具标签 OR 新对象作为交接；旧背景能满足背景检查 |

F4 的旧背景不是任意虚构的接口条件：运行器读取 `goals[0]` 的背景，再将其与本轮对象数量增量组合（eval-intent-ui.mjs:183），没有绑定到本轮新建目标。当前测试还有一条直接规定“读不到 created、unknown 不算失败”；这与真实对象验收要求冲突。

建议：下一版判据必须区分通过、失败、观测不足；背景只能由绑定到本轮新目标的持久化字段证明，回答用来评估表达；入口需要核对同一目标 ID。语义项若无法可靠自动判断，应留人工复核项，不能以关键词命中宣称产品验收通过。无需把判断改成简单的“必须出现问号”，没有问号也可能是在请求有效信息。

## 3. 指定的运行器尚未实现两轮验收

冻结稿指定 `eval-intent-ui.mjs`，但当前文件：

- :22 读取旧 `eval-intent.fixtures.json`，未读取 LN12/LN16 的二轮回复。
- :75 每个 case 都执行 `newChat()`，随后只发送一次 `c.question`。
- :188 调用 score 时仅传 text、工具标签、created，未传新判据所需的 createdDelta、goal、expectedPoints。
- 没有同一案例内保留对话、补固定背景、重放同一批准动作并检查重复创建的执行步骤。
- 新账号只在整批开始时创建，案例之间仅新开对话；未实现冻结稿要求的逐案例业务状态隔离。

因此目前完成的是“两轮输入文档和部分判据函数”，不是可直接运行的两轮验收。仅把 LN12-a/b 添加为独立 case 会丢失同一会话上下文。

另有统计风险：:172 只凭“无正文且无工具卡”推断 upstreamFailed，未要求关联错误日志。产品决定 §4 要求错误证据，故这一推断不能自动成为排除分母的依据。此处指出规则漏洞，不重判历史两条上游故障。

建议在联网前完成独立两轮运行器及离线契约检查：案例间隔离、案例内保留会话、真实对象 ID 前后差集、背景与入口核对、同一动作重放防重、请求关联日志及独立归档。用模拟观测证明采集与判定连接正确，不能把这些离线检查写成模型或 UI 验收。

## 4. 查询修复影响面超过已有验证

`book-verify.ts:107–108` 无条件删除书名中的全部空白。现有测试 :76 甚至把 `Thinking Fast and Slow` → `ThinkingFastandSlow` 固化为期望。

这是明确存在的原始词边界丢失，且发生在共享调用方，作用于所有搜索提供方；不是只对 Bing 应用的回退策略。两本中文书的命中不足以证明该策略适合外文书、含空格标题或同名书。本次没有联网验证，**不宣称外文书一定检索失败**。

建议保留规范书名的内部空格；把已有证据支持的查询变体作为受控策略，明确适用条件。对外文多词书名、中文标点、同名不同作者补验证；作者匹配等原有核查规则继续保持。测试应覆盖检索输入保真与可信结果判定，不能仅锁定“全部去空格”这个实现。
