### 4.4 in13 调查结论（按产品决定 §3 固定书架初态后）

**方法：** 新账号（书架为空），直接调用真实 `executeTool("add_book") + executeAction`，绕开模型，分离「工具能力」与「模型意愿」。

**结果：**

| 步骤 | 实际结果 |
|---|---|
| `executeTool("add_book", {title:"影响力", author:"罗伯特·西奥迪尼"})` | ✅ 成功生成待确认卡 |
| `executeAction(...)`（相当于用户批准） | ❌ 失败：「没有找到《影响力》的可信图书来源…」 |
| 书架数量 | 0 → 0（未创建） |

**根因：搜索服务退化，不是 add_book 逻辑或模型问题。**

实测 `/api/search`：

| 查询 | 返回 |
|---|---|
| `影响力 罗伯特·西奥迪尼 豆瓣` | MSN 蜘蛛纸牌、游戏攻略、图片 CDN |
| `影响力 西奥迪尼` | 模板站、百度文库、PPT 模板站 |
| `思考快与慢 卡尼曼` | poki.com 小游戏站 |
| `douban 影响力` | 豆瓣首页、电影首页（无图书条目） |

`verifyBook` 要求命中可信书目域（douban.com / baidu baike / wikipedia 等）的**具体条目页**，而搜索只返回站点首页或完全无关页面 → 核查正确判定 insufficient → `add_book` 正确拒绝。

**因此本复现证明的是：当前加书链路存在故障（搜索结果污染导致核查必然失败）。**

**结论边界（按用户收紧要求 + 归档工具标签证据）：**
- v2 归档留存了每案例的**工具标签**（非参数级）：原 in13 案例 tools = `["恢复工作流","看书架"]`——**模型确实未调用 `add_book`**（标签级证据，足以证明「未调用」；不足以还原调用参数与中间过程）。
- 因此原回答「这一轮我没法直接把它建进系统」**不是工具失败的转述**——它压根没尝试。可能的诱因是工具描述中「耗时较长/核实不过会被拒绝」的警示使模型保守（待冻结运行验证），此为假设、非结论。
- 单独复现（§4.4 前半）证明的是**当前加书链路故障**（搜索污染导致核查必败）；结合归档标签，原案例是「未尝试调用」+「若调用也会因搜索故障失败」的叠加。
- **不能直接把原回答认定为「诚实转述」**——原 `handoffHappened=false` 判定保留不变。
- **不通过放宽书籍核查来让加书通过**——核查纪律（PRD §5.4）保持不变。

**对照：in14 的工具标签 = `["加书上架","联网搜索"]`**——它**确实调用了** `add_book`，且书架增量 0，与「搜索故障 → 核查失败 → 正确拒绝」因果一致（in14 的空正文问题另见 §4.5）。

**仍需处理：** 搜索链路退化根因（无关结果从哪一层进入）见 **[搜索链路排查报告](./SEARCH-CHAIN-INVESTIGATION-2026-11-11.md)**（2026-11-11 已完成：根因 = Bing 对多词查询反爬降级；已修查询构造并通过搜索层验证《影响力》《思考，快与慢》均 verified，判定纪律未放宽）；原案例工具调用未留存的问题，需在冻结运行中让评测器留存每案例的工具调用序列。

### 4.5 in14 调查结论（按产品决定 §4 查四处）

**观察：** 工具卡 `加书上架`、`联网搜索` 都出现了（说明工具确实执行），但 `textLen: 0` —— 助手回答正文未取到。

**逐项排查：**

| 排查点 | 结果 |
|---|---|
| 评测器取数 | ✅ 可用。`Markdown` 组件确实渲染 `prose-mentora` 类（`markdown.tsx:56`），选择器有效 |
| 上游返回 | ⚠️ dev 日志出现 3 次 `POST /api/chat 500` |
| 流式结束 | 500 直接失败，无流可结束 |
| 消息保存 | 无回答可保存 |

**500 根因（dev 日志原文）：**
```
Error: Export READING_RAG_BLOCK doesn't exist in target module
  at src/app/api/chat/route.ts:15
⨯ ReferenceError: READING_MODES is not defined
  at src/app/api/chat/route.ts:76
```

**核实：** 这两个符号**当前都存在**（`READING_RAG_BLOCK` 在 `prompts.ts:1054`，`READING_MODES` 在 `reading-modes.ts:12`），且复测 `POST /api/chat` 返回 **200 正常**。

**结论（按用户收紧要求，暂不定根因）：** 模块加载错误，**疑似与并发修改有关**——500 堆栈显示导出缺失，而相关符号现在存在、接口恢复 200。但这不足以确认根因就是热更新：**500 与具体请求之间没有建立关联**（无法证明哪次请求对应哪个案例）。

**处置：**
- in14 保留为**未完成**，不标通过，不改故障分类。
- 故障记录为「模块加载错误，疑似与并发修改有关」。
- 冻结运行的批次中若再出现 500，必须留存请求↔案例关联与完整堆栈，才能重新分类。
