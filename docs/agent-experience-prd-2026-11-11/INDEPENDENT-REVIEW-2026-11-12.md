## 2. 三个已独立复现的代码缺陷

### R1：审批执行边界仍默认放行（优先处理）

位置：`src/lib/agent/runner.ts:395–412`，条件仍是 `if (!d || d.approved)`。

探针调用真实 `runAgent`，模拟工具返回一个待审批 `save_note` 动作，让审批回调返回空数组：**预期 executeAction 0 次，实际 1 次。** 两个对照分别显式批准/拒绝，实际写入调用分别为 1/0，均符合对照预期。

这证明执行边界缺少默认拒绝，不等于已证明当前正常界面一定会产生空决定。将决定移入按会话审批门修掉了一个触发来源，执行层仍须守住自己的边界。

执行要求：需要审批的动作必须收到匹配当前用户/会话/run/action 的明确批准。缺失、未知 action、过期决定和停止后到达的批准均不得写入。PRD 允许按用户原授权直接执行的小改动，应由独立且可检查的授权分类进入执行；**不能以“缺少审批决定”代表原授权已足够**。

验收：现有正常批准/拒绝保持通过；新增空决定、部分决定、未知 action、旧 run 决定、批准与停止竞态的行为测试，实际写入次数/对象差异符合授权范围；取消与重复批准不得增加副作用。再通过真实 UI 双会话审批验证。

### R2：首次登录身份登记没有设置用户作用域

位置：`src/lib/agent/session-runtime.ts:293–301`。首次调用在更新 `runtimeUserScope` 前 `return`。

独立新模块实例中执行 `resetRuntimeForAccount('user-A')` 后 `beginRun('session-A','run-A')`，**预期标记键 `user-A:session-A`，实际 `anon:session-A`**。

执行要求：首次身份登记、匿名转登录、A→B、退出登录均正确设置作用域。旧运行清理使用旧身份，新运行只使用新身份。明确处理 store 身份切换与异步加载 runtime 的先后次序。

验收：首次登录、刷新恢复、匿名转登录、A→B→A、退出的作用域行为测试；不能只测试第二次切换。对照 localStorage 和运行视图，不能出现错误账户前缀。

### R3：读取当前用户中断任务会删除其他用户标记

预置 A/B 两组标记，A 调用 `markInterruptedOnLoad()`：返回 A 会话正确，但 **B 标记也被删除**。

执行要求：只消费当前账户已经处理的条目，保留其他账户标记。

验收：A 恢复后 B 标记原样保留；随后切 B 仍可恢复自己的中断提示；不得自动重放任何写动作。历史匿名键如需迁移，不能把未知归属标记直接认领给当前用户。
