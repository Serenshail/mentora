## 1. 为什么不直接改 DB_CHANNEL

`src/lib/server/db.ts:536–566` 表明 `huawei` 不只是另一条网络线路：users/data/versions 等转向 RDS，rl/code/quota/loginfail 转向 DCS。只有 RDS 凭据不够，DCS 的 REDIS_URL 也要配置。切换不等于迁移已有账号和学习数据。

要使用现成测试环境，执行者先确认：独立测试进程及端口；专用数据库与 Redis 实例或可靠独立命名空间；测试凭据权限不覆盖真实数据；测试认证与浏览器状态独立；清理范围只包含本批 fixture。仅改端口、只建新账号、或仍共用真实 RDS/DCS，均不构成完整隔离证明。

已有隔离环境可继续使用；没有就不为这三个用例另起大型部署或迁移。不要修改共享 `.env.local`、线上环境或复制真实账号数据来解决验收阻塞。

D1 官方说明免费日额度在 00:00 UTC 重置，即北京时间 08:00。本次 11 月 12 日晚间阻塞对应的下一次重置为 **2026-11-13 08:00（北京时间）**。重置不保证服务自动正常，恢复后只做一次最小健康检查，成功再跑流程。来源：[Cloudflare D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/)。

## 2. 恢复前必须修掉的脚本问题

### 2.1 审批等待顺序会相互卡住

真实脚本 `ask()` 约 319–359 行只在“发送按钮重新出现且消息稳定”时返回；A04 在约 410 行先 `await ask()`，432 行才 `approveIfPresent()`。mock 脚本也是先等 ask 返回再批准。

正常结构性修改停在 awaiting_approval 时仍忙碌，runner 等用户决定，脚本却等 runner 结束。因此**语法通过不代表流程可运行**。这是本次静态检查发现，尚未做浏览器动态复现。

执行者拆成如下步骤，不写一套统一“等 idle 再处理一切”的 helper：

1. `send` 后固定 sessionId/runId，保留本轮开始位置。
2. 等待该 run 出现审批卡或真实终态；看到失败/中断及时退出并留证。
3. 若审批：采集准确草稿、actionId、版本、完整业务快照，验证未写入，再按场景批准/拒绝/制造并发冲突。
4. 决定发出后才等待同一 run 的最终状态，采集真实字段差异。
5. 若只给自然语言草稿且已结束，记录“尚无可应用动作”；允许用户按固定输入补一句明确授权，再验证模型是否形成准确审批动作。不能把一张文字表格认作可执行预览。

先用可控假上游完成等待审批、拒绝、批准、异常四条机制路径；超时采集当前 run 状态、卡片、已接受正文和事件，不只抛出 ask timeout。

### 2.2 “完整快照”仍是字段投影

真实脚本 `objectSnapshot()` 只取部分字段：知识点仅 id/text，验收记录仅部分 items，catalog 仅 id/title，Rust 仅阶段标题。这不能证明掌握证据、讲义、完整验收、关联关系和干扰对象未变。

改为保存隔离测试数据的完整可序列化业务对象，深比较时只排除事先列明的允许变化路径，不能事后扩大白名单。只改标题允许：指定 title、已约定的修改时间/版本、新增的正确快照。其余阶段、学习日及所有知识点证据、成绩、笔记、关联和 Rust 目标应逐字段一致。历史原条目不能被替换，只允许新增应有条目。

这里全为合成 fixture，不需要为了脱敏删掉决定正确性的字段；凭据/cookie 不进快照。

### 2.3 A04 当前有容易误报通过的断言

- 批准前只比较 phases 和天数：应比较整个业务投影并确认新增/更改路径为空，聊天及临时审批 UI 独立记录。
- 成绩 `length>0`、笔记存在：应比较原记录 ID、内容、证据、关联和掌握信息。
- 专业页 `/第二阶段|文件/`：旧页面也能命中。必须验证本轮新目录及稳定目标/阶段 ID，打开具体日程查看实际内容。
- 刷新只比 phases 和 days 数量：应与批准后完整预期对象比较，不能在刷新前后再次 seed。
- 模型写“每天半小时”不代表落库成功：定义实际工时字段或具体可追踪任务安排，检查草稿、批准 payload、落库、页面四处一致。若系统无分钟字段，明确记录限制并按可验证任务预算验收，不新增无关工时系统。
- 已完成一天继续保留应看稳定 dayId 与完整数据；不能仅依赖标题相同或总数相同。

“7 天”沿用冻结用例的实际业务口径；不要在跑完后改成只有 estDays=7 也算完成。

## 3. 零 D1、零模型的验证范围

机制验证在自动化测试中使用测试专属数据库 adapter 或对实际边界的可控替身，走真实页面、工具执行器和审批状态机。测试替身只在独立测试进程/测试配置启用，不给线上加免登录后门，不靠签一个 token 假装 verifySession 不再查库。

完全模拟 auth/sync 时明确标为 L2 机制验证，不能用于证明真实注册、真实云同步或远端持久化通过。刷新保持若只来自 localStorage，也只报告本地持久化。

优先复用现有测试注入能力；若当前没有且改造超过本批收益，先用现有 L1 组件/执行器测试完成审批交互和差异断言，保留真实 L2 BLOCKED。不要为解一个临时配额问题重构整套存储。

完成标准：审批阶段未结束也能取证；批准/拒绝分别走通；旧草稿冲突拒绝；已完成成果逐字段保留；目标对象与刷新验证不靠反复注入。机制通过后才启用真实模型。

## 4. 录屏不要成为新的研究项目

PNG 序列有辅助价值，不等同连续操作录像；必须正确标注，不能放进 videos/ 就算满足合同。视频格式可为可播放的 WebM，**不要求 MP4**。

给执行者一次有边界的修复：核对实际使用的 playwright-core 版本及其匹配浏览器/ffmpeg 安装缓存，使用同一版本配套工具，完成 10 秒无敏感信息的可播放录像与 close 后文件落盘验证。不要反复猜环境变量或盲装不同 revision。

仍失败则采用已有可用的屏幕录制工具，对可见独立测试浏览器录制一次实际连续操作；没有可用工具就继续事件/对象证据工作，录像保留待补，不伪称完成。把事后 PNG 拼成视频也不能冒充真实连续录制。

## 5. 恢复后只跑固定的最小批次

1. 健康检查确认读、认证、水合、同步可用；已知日额度耗尽不做五次同样注册重试。预先准备和复用少量隔离测试账号，不每条场景重新开码。
2. 机制验证先通过；固定源码/脚本/fixture 摘要与 batchId，核清本批 provider 预算。
3. 同一真实对话跑 A03→A04：含糊调整→聚焦澄清且零写入→固定补充“第二阶段一周、每天半小时、保留已完成”→精确草稿→批准→专业页→刷新。保留所有首次失败，不拆成互无背景的两次问答冒充连续闭环。
4. 单独 A01-E4：明确改标题→仅指定字段变化→专业页→刷新，全对象对照及 action/版本齐备。
5. 出现确定性脚本/fixture 问题先停本批，修正后另记 attempt；不让多轮模型反复补偿脚本错误。

PowerShell 中使用 `$env:PHASE='a03'` 等有效语法；原文 `PHASE=a03|a04|a01e4` 是选项说明，不能原样当可运行命令。每次指定新 OUT，避免覆盖已封存 run-d。
