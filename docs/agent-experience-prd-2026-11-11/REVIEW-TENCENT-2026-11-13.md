## 2. 同步写入路径仍有高风险，先做行为复现

定点阅读当前 `src/lib/auth-client.ts` 发现：

1. `useAutoPush` 等待 `bootSync()` 后无条件 markReady；而 `bootSync()` 内部 catch 错误并返回、拉取 error 也返回 void。**拉取失败与安全完成对调用方不可区分**，后续 store 变化仍可触发推送。现有 `agent-autopush-firstsync-gate.test.ts` 是源码正则，测试名声称“失败不放行”，断言实际上只检查 markReady 存在，不能证明失败不放行。
2. `useFlushOnHide` 直接 `pushCloud`，没有使用同一首轮同步闸门。读取尚未成功时切后台、pagehide 路径需要独立验证。
3. `syncAfterLogin` 在检查 `cloud.status === error` 之前，用 store 引用变化决定直接推送；需要验证慢登录/水合与拉取失败场景，不能只改 bootSync。
4. bootSync 在拉取期间真实用户编辑可能被 import 覆盖；仅有 state 引用变化又分不清水合与业务编辑。当前注释说由后续自动推送承接，但订阅在 ready 前直接忽略变化，且 import 可能先覆盖。必须用受控竞态复现后设计，不按注释认定安全。

以上是代码路径与风险判断，**没有在本轮独立复现真实数据丢失**。执行者在隔离 PG/Redis 测试环境写非空合成云数据，在开始前冻结完整初态并保存快照，逐项验证：

- GET 延迟/超时/503/认证变化时，水合、初始化、切后台及 pagehide 后没有向云端写入旧或空快照；恢复后用户修改仍能同步。
- 拉取期间用户真实编辑，云端和本地各自包含不同记录：不得静默覆盖任一方；明确可恢复的冲突/合并策略并验证。
- 首次无数据、仅设置或提醒、仅对话、已有学习和笔记等状态正确识别，不能把有效数据误判为空。
- 多个 `bootSync`/login/flush 并发或切账号时，旧账号迟到结果不得影响新账号。
- 任一同步结果声明、时间水位和真实写入一致；断网时保留草稿并向用户展示实际状态。

以行为测试与真实浏览器可控网络证据锁定以上路径；源码正则可保留为辅助，不能代替行为测试。未经这些验证，不宣称“生产级数据丢失已修复”。

## 3. 跨设备冲突是优先级高的待查问题

现有 `applyPhaseEdit` 的 baseSignature 比对本地 store；`/api/sync` 是整份快照写入，需查实际服务端并发控制。A04M-l 实测写回旧标题，但样本中远端修改与本地不一致，**只能说明现状未证明跨设备冲突防护**，不能根据一个脚本直接断定所有跨会话都失败。

在独立测试环境用两个真实登录的浏览器上下文和同一测试账户验证：A 打开精确修改预览；B 保存另一项已确认修改；确保 B 写入成功并有服务端版本；A 批准后不得无提示覆盖 B。验证并发写入边界以及刷新后 A/B/服务端最终状态，保留两个方案和数据。若冲突存在，设计服务端原子条件写入/版本冲突反馈，并确保通用同步也不能绕过保护；仅在客户端 GET 后再写不提供原子保证。冲突时保留草稿并允许用户重新预览，禁止静默覆盖。
